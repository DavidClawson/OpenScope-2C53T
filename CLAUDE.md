# FNIRSI 2C53T Open-Source Firmware Project

## What This Is

Reverse engineering and clean-room rewrite of the firmware for the **FNIRSI 2C53T**, a 3-in-1 handheld oscilloscope/multimeter/signal generator. The original firmware was decompiled from binary using Ghidra and is being refactored into clean, modular C.

## Hardware Target

- **MCU:** Artery AT32F403A — ARM Cortex-M4F @ 240MHz, 1MB flash, 224KB SRAM (with EOPB0=0xFE)
  - Originally identified as GD32F307 from firmware analysis; physical teardown revealed AT32 (markings sanded off)
  - Register-compatible with GD32/STM32F1 at the GPIO/EXMC level
- **LCD:** ST7789V 320x240 RGB565 via 16-bit parallel EXMC/XMC bus
- **FPGA:** Gowin GW1N-UV2 (non-volatile, retains bitstream across power cycles) — handles 250MS/s ADC sampling via **SPI3 data + USART2 commands**. NOTE: stock firmware nonetheless **uploads a fresh FPGA configuration over SPI3 at every boot** (the 0x3B/0x3A bulk exchange) — the NV image alone services USART meter traffic but **NOT scope capture — this is now an experimental FACT, not an inference (2026-07-27).** Single-byte ablation of stock (`0x15` CONFIG_ENABLE → `0x11` READ_IDCODE at file offset `0x26A42`, so the FPGA keeps its NV design) gave a clean A/B/A on bench unit #1: clean stock → scope works; ablated stock → **scope stone dead, no trace**, meter fine (4.11 V cell); reflash clean → scope works again. Same probe/cell, one byte different. The resident NV design is meter-only; scope depends entirely on the boot reconfig. Corollary: the same `0x15→0x3B→0x3A` sequence *takes* on stock but is *refused* on our firmware (STATUS pinned 0x00039020, EDIT_MODE never engages) ⇒ the deciding factor is **FPGA state when CONFIG_ENABLE arrives, not the bytes.** **Experiment B2 (2026-07-27) REFUTES the timing-window theory:** a verified code-cave CPU busy-loop pushed stock's config-enable ~5–10 s later (visible splash→menu pause) and the scope still came up fully working ⇒ the FPGA accepts config-enable ≥6–12 s post-power-on; no narrow window. So the blocker is a **signal/state difference**, not bytes or timing. Everything firmware-reachable is now excluded (bytes, framing, prelude, trailing clocks, timing). **The user-mode-lockout candidate is REFUTED — do not re-chase it** (rediscovered 2026-07-27): the `FPGA_USART_SILENT_SCOPE=1` bench build (USART2 UEN never set, zero pre-config USART traffic — i.e. exactly the "no user-mode traffic before CONFIG_ENABLE" condition) was run **2026-06-13 and changed NOTHING; the config-entry wall was identical.** See `master_init_decode_diff_2026-06-13.md`. ### Normal dev cycle (case closed)
1. On device: Settings → Firmware Update (shows "BOOTLOADER MODE" screen)
2. On host: `cd firmware && make flash`
3. Device auto-reboots into updated firmware

### First-time setup
Two bootloader modes exist — don't confuse them:
- **ROM DFU** (BOOT0 + pinhole reset, LCD dark, `2e3c:df11`): only mode that can write option bytes. Required once.
- **HID bootloader** (Settings → Firmware Update, or POWER+PRM during reset, "BOOTLOADER MODE" LCD): used by `make flash` for all normal updates. Cannot write option bytes.

1. Enter ROM DFU (BOOT0 jumper to 3V3, pinhole reset). Verify: `dfu-util -l` shows `2e3c:df11` with alt 0 and alt 1.
2. Set EOPB0=0xFE (224KB SRAM): `dfu-util -a 1 -d 2e3c:df11 -s 0x1FFFF800 -D firmware/build/option_bytes48.bin` (48 bytes, generated by `make`; the region size is literally 48 bytes per the DFU descriptor `01*048 e` — a shorter file gets rejected with "address out of range").
3. Flash bootloader + app: `make flash-all`
4. Close the case — all future updates go over USB-C.

### Addressing convention (READ THIS FIRST — corrected 2026-07-28)

**The stock app binary is linked at `0x08007000`.** For `APP_2C53T_V1.2.0_251015.bin`, file offset `N` = flash address `0x08007000 + N`. Verified from the app's own vector table: word0 = `0x20036F90` (initial SP), word1 = `0x08007311` (Reset_Handler, Thumb bit set), and every subsequent vector points into `0x08007xxx+`.

Historically this repo mixed **two** conventions, both written as a bare `0x08xxxxxx`, with nothing marking which was which. That ambiguity is the root of the `0x7000` class of bugs (see the H2 bitstream saga below, where a real flash address was misread as a file offset):

| Convention | Where it came from | Conversion to flash |
|---|---|---|
| **Flash** (correct as written) | objdump, SWD, bench work, and pointer literals embedded in the code | none needed |
| **Legacy Ghidra** | the old `ghidra_project` import, which was loaded at base `0x08000000` — so its addresses are really *file offsets* | **add `0x7000`** |

`reverse_engineering/analysis_v120/function_names.md` and `function_map_complete.txt` are entirely in the **legacy** convention — add `0x7000` to every address in them. (Validated: of 301 entries, 291 land exactly on function entries after the shift and 290 of those also agree on function size.)

**The Ghidra project has been fixed (2026-07-28).** Use the program **`APP_2C53T_V1.2.0_base08007000.bin`** in `ghidra_project/` — imported at `0x08007000`, so *Ghidra addresses now equal flash addresses*, with 302 of 384 functions named and the bitstream blob defined as `FPGA_BITSTREAM_gowin_fs`. The older `APP_2C53T_V1.2.0_251015.bin` program in the same project is the legacy-base import; **do not read addresses off it.**

Stock factory upgrades must have used ROM DFU or a separate bootloader binary not present in `APP_2C53T_V1.2.0`. **The "caseless bridge flash" idea is infeasible** — new units need ROM DFU (BOOT0 + reset) or SWD once; after that our HID bootloader handles everything.

5. **`reset_and_clock_init.md`** — Decoded the reset handler and clock init at flash `0x08007000–0x08007238` (legacy `0x08000000–0x08000238`; note the real `Reset_Handler` entry is at `0x08007310`, just past that range — the range covers the vector table and early startup). **240MHz confirmed**, but via a different PLL path than ours: stock uses `HEXT ÷ 2 × 60 = 240MHz` (pllhextdiv=1, pllmult_l=11, pllmult_h=3 → 11 + 16×3 + 1 = 60). Our firmware uses `HEXT × 30 = 240MHz`; both produce the same SYSCLK. Stock is built with **Keil MDK (ARMCC)**, not GCC — explains the scatter-load layout, TBB jump tables, and absence of an explicit `SystemInit()`. No firmware changes needed.
