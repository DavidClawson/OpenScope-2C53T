## 6. FPGA dev board (arrives in the same package)

Strategy decided 2026-08-20 (see discussion): **hybrid — stock-RE becomes the
spec, our own bitstream becomes the product.** Key fact shaping everything:
the SSPI config handshake (0x11/0x15/0x3B/0x3A) is the Gowin **silicon config

existing bit-bang loader unchanged. The runtime protocol (SPI3 reg file,
0x04/0x05 reads, arm) is fabric and exists only in stock's design.

### The rig: Blue Pills + Tang Nano 20K (board identified 2026-08-20)

The dev board is a **Sipeed Tang Nano 20K** — GW2AR-LV18QN88 (**Arora
family, NOT GW1N/LittleBee**). Same UG290 silicon config engine and SSPI
command set, so every front-door experiment transfers; different IDCODE and
incompatible bitstreams, so **M0 builds for GW2AR-18** (a flagship apicula
target) and **M1 still needs a GW1N-2 build** for the 2C53T. Per project
method, anchor every SSPI session with an IDCODE read (`0x11`) first —
expect a GW2A code, not `0x0120681B`.

From the v1.3 schematic (local copy:
`docs/datasheets/tang_nano_20k_schematic_v1.3.pdf`; pin mapping verified
by power/MSPI alignment — re-verify by continuity on arrival):

- **All four SSPI config pins are on one 20-pin edge header — zero solder**:
  FPGA pin 55 `SSPI_CS_N` (hdr 11), pin 52 `SCLK` (hdr 20), pin 54 `DIN`/SI
  (hdr 8), pin 56 `SO` (hdr 7); pin 53 `DOUT` (hdr 19) for completeness.
  Bank VCCO is 3V3 — no level shifting against a Blue Pill. The nets are
  shared with I2S/EDID-labelled peripherals (audio amp, possibly HDMI DDC):
  keep HDMI unplugged during SSPI runs and check what else hangs on them.
- **MODE0/MODE1 are the two user buttons** (FPGA pins 88/87, pulled, 1K
  series) — config mode is strap-selectable with no iron. To do on arrival:
  look up the GW2A SSPI-slave MODE value in UG290 and the button/pull
  polarity (R4–R7).
- **RECONFIG_N** = FPGA pin 9, net `SYS_RECFG`, resistor-terminated but NOT
  on the edge headers — locate its pull pad under the microscope if an
  experiment needs to drive or watch it. For the first time this signal is
  observable at all.
- **Onboard 64 Mbit flash on the separate MSPI pads (59–63)** — the board
  can be prepared blank OR auto-booted-from-flash, i.e. we can manufacture
  the exact state the 2C53T's part was always stuck in (see BIS-4 below).
- **BL616** = the USB JTAG programmer: an independent config oracle and an
  un-brickable recovery path. Its "HSPI" nets (FPGA pins 13/75/76/86) are a
  Sipeed fabric data link, **not** config SSPI — do not confuse the two.

**Target tiering (decided 2026-08-20):** the quirk we are chasing is by
definition undocumented, so "same documented protocol" is weaker assurance
than "same silicon family."

- **Tang Nano 20K** (in the mail) — Arora. M0 toolchain proof + first
  bisect target. Fidelity miss: boots from EXTERNAL MSPI flash, while the
  scope's GW1N-UV2 auto-boots from EMBEDDED NV flash — the one mechanism
  BIS-4 is about.
- **Tang Nano 9K** (ordered 2026-08-20, ETA Mon 2026-08-24) — GW1NR-9,
  LittleBee, WITH embedded config flash: same family engine and same
  auto-boot path as the scope's part. Runs the family-faithful BIS-4, and

  engine's auto-booted state or of stock's specific design. Also rehearses
  the NV-flash write workflow with zero stakes (see below). No cheap

  9K=GW1N-9).
- **Differential value of owning both:** a result on both boards is
  family-independent engine behavior; a result on the 9K only is
  LittleBee-specific. Either way the quirk gets localized — one board

- **Second 2C53T** (deliberate later option, not ordered) — the exact-part

  (4) BIS-3 confirmation soldering at the scope's own 0.5 mm pins; (5)

Driver: **Blue Pill (STM32F103, on hand)**. The AT32F403A is STM32F1-family

### The config-transport bisect (dev board + logic analyzer)

Why it matters: stock 2C53T configures through the **hardware SPI3 peripheral
at /2** (Exp E, CTRL1 BR=0) — the very peripheral that failed for us for two
months — while the working Build B is a transplant of the **2C23T sibling's**
GPIO bit-bang loader. So the fix is not "GPIO beats peripheral"; it is a
bundle of three changes that have never been separated. Build A (hardware SPI
at /256, byte-identical framing, FAILED) already excludes raw clock speed.

Three suspects, one experiment each, single-variable, on the dev board first
(zero risk) then confirmed on the 2C53T (power cycle restores NV):

- **BIS-1 — prelude reads.** Hardware-SPI transport + the V0.4 prelude
  (`0x11 → 0x13 → 0x41` before `0x12`/`0x15`). Works ⇒ the engine needs a
  read transaction to sync before config entry.
- **BIS-2 — the missing `0x05`.** Hardware-SPI transport, our original prelude,
  ERASE_SRAM omitted. Works ⇒ our `0x05` was actively poisoning entry, not
  inert. Cross-check: bit-bang transport WITH `0x05` added — if that now
  fails, `0x05` is confirmed the whole story.
- **BIS-3 — the waveform.** Bit-bang transport, byte-identical sequence, and a
  logic-analyzer diff against the hardware-SPI capture: inter-byte gaps,
  CS setup/hold vs first/last clock edge, clock idle state across CS, edge
  rates (GPIO drive vs AF). If BIS-1 and BIS-2 both fail, this is what's left —
  and it is the one layer byte-level fidelity work was structurally blind to.
  (HiLetgo 24 MHz is ample at /256 and for bit-bang; NOT for /2 — keep the
  hardware-SPI leg at /256 for capture runs.)

- **BIS-4 — the state bisect (dev board only).** Blank part vs
  auto-booted-from-flash part × hardware-SPI vs bit-bang transport. Every
  one of our four months of refusals was against a part that had auto-booted
  its NV design — a state we could never undo (Exp R: even a true power
  cycle didn't open the port). The Tang Nano 20K's onboard flash lets us
  manufacture both states at will. If hardware-SPI works on a blank part but
  fails on an auto-booted one while bit-bang works on both, that is a
  MECHANISM, not a correlation — with RECONFIG_N, DONE-equivalent status,
  and the MODE straps finally observable while it happens.

Decision rule: run BIS-1 and BIS-2 on the dev board in one sitting (they are
firmware-only variants of existing builds); only if both fail invest in the
BIS-3 capture rig. Any positive ⇒ re-run on the 2C53T, then retire the bit-bang
path or keep it with a documented reason. Bonus stake: the CDC failure
correlates with the hardware-SPI config path (CLAUDE.local.md, replicated on
a second unit in PR #13) — whichever suspect wins here is also the leading
candidate for that mechanism.
