# Development Plan — post-cold-boot phase (2026-08-13)

## Why this plan exists now

Config entry was the project's critical path for four months. It is solved: cold boot →
configured FPGA → live capture on both channels, reproducible on bench unit #1
(`0x0003F460`, DONE_FINAL set). The FPGA-first priority stance that deferred UI and DMM work
was contingent on that, and it is now satisfied.

That unblocks a large backlog at once. This plan organises it into **parallel workstreams that
do not need bench hardware**, so agents can work them concurrently, plus a separate queue of
bench-gated items that only the maintainer can run.

## Ground rules for anyone (human or agent) working this plan

1. **You do not have the bench.** Bench unit #1 is a single physical device. If a task's
   acceptance criteria require observing hardware, it belongs in §F and you must not claim it
   done. Say "ready for bench validation" instead.
2. **Do not touch the config path.** `fpga_spi3_config_sequence()`,
   `fpga_bitbang_config_sequence()`, and their option structs are bench-validated and fragile.
   Four months of this project's history is encoded in their comments. Changes there are
   maintainer-only.
3. **Do not move `SHMEM_FFT_WATERFALL_OFFSET` or pool sizes** without understanding the
   `_Static_assert` in `fft.c`. It exists because the obvious constant (`SHMEM_NEED_FFT`) is
   wrong for the radix-2 layout, and it has already caught one real collision.
4. **Run the gate before claiming anything passes:**
   `python3 scripts/run_tests.py --strict` — must be 9/9 suites, **zero skips**. If artifacts
   are missing, build them (`firmware/bootloader`, `bootloader_updater`, `stock_dispatcher`,
   `high_layout_updater`); do not accept a skip.

   **⚠ But know what that gate does NOT cover (found 2026-08-13).** All nine suites test the
   IAP/bootloader/stock-image tooling. **None of them compiles `firmware/src`.** A green gate is
   compatible with firmware that does not build at all — this was demonstrated, not theorised: a
   malformed comment in `flash_fs.h` broke every TU that included it and the gate still reported
   10/10, because `test_flash_switcher` reads the *last built* image and that image was stale.
   So the gate is necessary and not remotely sufficient. Rule 5 is what actually protects
   firmware changes, and if you touch `src/` you must also bring your own test (see rule 6).
   Closing this gap — a suite that compiles the firmware — is itself a worthwhile task.
5. **Build every target you could have affected:** `make guest`, `make`, `make emu`,
   `make -f Makefile.hwtest`, `make -C bootloader`. `guest` is the bench build and must stay
   warning-clean.
6. **A clean build is not a passing test.** This project's recurring failure mode is
   instruments that report confidently on state they cannot observe (the `/2` status reads, the
   floating MISO, the `status` shell printing a refusal on a configured device, a flash test
   that depended on which target built last). If you add a check, make it fail when it should —
   demonstrate that, don't assume it.

## §B — Rendering pass (biggest UX win, fully testable in the emulator)

Long-standing TODO, now with a concrete measured example.

### B1. Waterfall render — **20,480 `lcd_fill_rect` calls per frame**
`scope_ui.c:draw_waterfall_screen()` clears the plot to black, then draws every pixel column as
an individual 1×`row_height` fill. Bench-observed 2026-08-13: the fill is visibly rastered
left-to-right, top-to-bottom, taking seconds per frame.
**Fix direction:** build a row of RGB565 into a line buffer and blit per row, or per changed
row only (the history scrolls by exactly one row per frame — 63 of 64 rows are unchanged).
**Acceptance:** measurable reduction in draw calls; emulator shows the same image.

### B2. Scope and siggen unconditional redraw
`main.c` still repaints these every loop; the meter was already fixed (throttled to data-change
events, 2026-04-04). Same treatment, or the component-level dirty tracking the TODO describes.
**Acceptance:** no full-area repaint when nothing changed; scope trace still updates live.

### B3. Waterfall colour scale
With `ref_level_db = 0` / `db_range = 80`, red = 0 dB and blue = −80 dB. A synthetic full-scale
square wave leaks across most bins, so the plot reads as a hot red field with thin nulls —
technically correct, visually useless. Consider auto-ranging the reference to the frame's
observed max, or a better default.
**Acceptance:** a 1 kHz square renders as recognisable harmonics on a dark floor.

## §C — Storage foundation (prerequisite for modules and user calibration)

### C1. W25Q region layer — **blocks C2, D1, and user-cal**
See `docs/roadmap.md` § "W25Q region layer". Not FatFs — a region table plus a bounds-checked
allocator. Requirements: explicitly **read-only** regions (factory cal at
`3:/System file/cal_ch1.bin` / `cal_ch2.bin`, stock UI assets) enforced **by address, not by
convention**; bounds checks on every write/erase; a designated scratch region; no-op-write
elision; append-style records for frequently-updated data.
**Context:** `flash_fs_read()` / `flash_fs_write_atomic()` are currently FatFs stubs — only the
raw primitives are live, addressed absolutely. Nothing writes at runtime today, so this can be
built before the first writer exists, which is the right order.
**Wear is not the constraint** (100k cycles/sector; the danger is a stray erase destroying
irreplaceable factory cal). **Acceptance:** host tests proving a write to a read-only region is
refused, and that a bounds violation fails closed.

### C2. Streaming screenshot
Screenshot is the only reason the pool is 150 KB (`SHMEM_NEED_SCREENSHOT = 153600`). Capturing
in row bands to SPI flash or USB would let the pool drop to the FFT need and free ~44 KB.
**Depends on C1.**

## §D — Modules (pure data, high community value, zero firmware risk)

Executable module code is **not achievable** on this hardware — the AT32 SPIM XIP window
collides with USB D−/D+ (see `docs/roadmap.md`). Modules are **data + a firmware-side
interpreter**, which is what `modules/` already is.

### D1. Module schema + loader spec
Define the JSON schema, the pool tenancy (`SHMEM_OWNER_MODULE` already exists), and the
interpreter's capabilities. **Depends on C1** for storage.

### D2. Seed modules
`modules/` has automotive, HVAC, ham radio and education stubs. Fill them out. This is the
single best contribution surface for domain experts who don't write firmware — CONTRIBUTING.md
already says so. Good candidate for splitting across several agents by domain.

## §F — Bench-gated queue (maintainer only, do not attempt)

1. **CDC single-variable test** — flash `guest-configB` (bit-bang, no warm-handoff). CDC up ⇒
   the culprit is `FPGA_CONFIG_B`; down ⇒ `FPGA_WARM_HANDOFF_TEST`. See `CLAUDE.local.md`;
   correlation is 5/5 with build type, mechanism unestablished.
2. **Per-range scope calibration** — the trace currently clips against the top of the window
   (baseline ~55, placeholder). Needs known signals at known amplitudes.
3. **CH2 trigger reference** — predicted to need TMR13 CH1 PWM on PA6 (`C1DT @ 0x40001C34`),
   which our firmware never programs. Decoded, unconfirmed.
4. **Timebase** — TMR3 is stock's acquisition pacer but ours is owned by the 500 Hz button
   scan; one must move before porting stock timing.
5. **PR #13 merge** — blocked on Komzpa's `SHMEM_POOL_SIZE` decision, not on bench.
