# Development Plan — post-cold-boot phase (2026-08-13)

## Why this plan exists now

Config entry was the project's critical path for four months. It is solved: cold boot →
configured FPGA → live capture on both channels, reproducible on bench unit #1
(`0x0003F460`, DONE_FINAL set). The FPGA-first priority stance that deferred UI and DMM work
was contingent on that, and it is now satisfied.

That unblocks a large backlog at once. This plan organises it into **parallel workstreams that
do not need bench hardware**, so agents can work them concurrently, plus a separate queue of
bench-gated items that only the maintainer can run.

## Ground rules for anyone (human or agent) working this plan

1. **You do not have the bench.** Bench unit #1 is a single physical device. If a task's
   acceptance criteria require observing hardware, it belongs in §F and you must not claim it
   done. Say "ready for bench validation" instead.
2. **Do not touch the config path.** `fpga_spi3_config_sequence()`,
   `fpga_bitbang_config_sequence()`, and their option structs are bench-validated and fragile.
   Four months of this project's history is encoded in their comments. Changes there are
   maintainer-only.
3. **Do not move `SHMEM_FFT_WATERFALL_OFFSET` or pool sizes** without understanding the
   `_Static_assert` in `fft.c`. It exists because the obvious constant (`SHMEM_NEED_FFT`) is
   wrong for the radix-2 layout, and it has already caught one real collision.
4. **Run the gate before claiming anything passes:**
   `python3 scripts/run_tests.py --strict` — must be 11/11 suites, **zero skips**. If artifacts
   are missing, build them (`firmware/bootloader`, `bootloader_updater`, `stock_dispatcher`,
   `high_layout_updater`); do not accept a skip. Runtime is ~25 s, most of it the firmware
   compile.

   **⚠ The hole this rule used to have is CLOSED (2026-08-13), but read why it existed.** Until
   that day every suite tested the IAP/bootloader/stock-image tooling and **none compiled
   `firmware/src`**, so a green gate was compatible with firmware that did not build at all.
   Demonstrated, not theorised: a malformed comment in `flash_fs.h` broke every TU that included
   it and the gate still reported 10/10, because the one suite that touched a firmware image
   (`test_flash_switcher`) read the *last built* artifact and that artifact was stale.
   Two fixes landed:
   - `scripts/test_firmware_build.py` compiles **`make`, `make guest`, `make emu`,
     `make -f Makefile.hwtest` and the bootloader**, from clean, each into its own
     `build-gate-*` directory, and checks each artifact's vector table. It has been
     demonstrated to go red on a syntax error, on the exact `flash_fs.h` comment bug, and on a
     newly-introduced compiler warning.
   - `test_flash_switcher` no longer asserts a fixed verdict against `firmware/build/firmware.bin`
     (156957b). That verdict used to flip on build order alone: FAIL after `make emu`, PASS
     after `make`, with no source change. Re-verified 2026-08-13 by reproducing the
     emu-then-gate sequence.

   Note what the compile suite deliberately does **not** do: it never writes to
   `firmware/build/`. The gate must not become the thing that populates the ambient artifact
   other suites read — that coupling *was* the bug.
5. **Build every target you could have affected:** `make guest`, `make`, `make emu`,
   `make -f Makefile.hwtest`, `make -C bootloader`. `guest` is the bench build. The gate now
   builds all five for you, so in practice this rule is satisfied by rule 4.

   **⚠ CORRECTED 2026-08-13 — this rule used to say `guest` "must stay warning-clean". That
   was never measured, and stating it as a standing fact invited agents to assume a baseline
   that did not exist.** The measured baseline at commit 9388e71, arm-none-eabi-gcc 13.2.1:

   | target | warnings in our code |
   |---|---|
   | `make` (app) | 0 |
   | `make guest` | 0 |
   | `make -C bootloader` | 0 |
   | `make -f Makefile.hwtest` | 1 — dead `power_hold_init()` in `src/attic/hwtest.c` |
   | `make emu` | 6 — `-DEMULATOR_BUILD` compiles out the callers of several tasks |

   (All five also emit four `_close`/`_lseek`/`_read`/`_write` newlib **linker** warnings. Those
   come from the toolchain's libc, not from this repo, and are excluded.) So `guest` happens to
   be clean today — but the earlier claim was true by luck, not by enforcement, and it was
   asserted while `emu` and `hwtest` were not.

   **The rule now enforced is a ratchet, not "zero warnings":** `WARNING_BASELINE` in
   `scripts/test_firmware_build.py` freezes the table above, and any warning not in it fails the
   gate. New code cannot add warnings; the existing ones are visible and countable, and pruning
   one after fixing it is a *passing* change. A hard zero-warning rule was considered and
   rejected: it would have forced edits to unrelated files (`main.c`, `usb_debug.c`,
   `continuity_buzzer.c`, an attic bring-up file) or invited a `-Wno-` suppression — either way
   the gate stops reporting on the thing it names.
6. **A clean build is not a passing test.** This project's recurring failure mode is
   instruments that report confidently on state they cannot observe (the `/2` status reads, the
   floating MISO, the `status` shell printing a refusal on a configured device, a flash test
   that depended on which target built last). If you add a check, make it fail when it should —
   demonstrate that, don't assume it.

## §B — Rendering pass (biggest UX win, fully testable in the emulator)

Long-standing TODO, now with a concrete measured example.

### B1. Waterfall render — **20,480 `lcd_fill_rect` calls per frame**
`scope_ui.c:draw_waterfall_screen()` clears the plot to black, then draws every pixel column as
an individual 1×`row_height` fill. Bench-observed 2026-08-13: the fill is visibly rastered
left-to-right, top-to-bottom, taking seconds per frame.
**Fix direction:** build a row of RGB565 into a line buffer and blit per row, or per changed
row only (the history scrolls by exactly one row per frame — 63 of 64 rows are unchanged).
**Acceptance:** measurable reduction in draw calls; emulator shows the same image.

### B2. Scope and siggen unconditional redraw
`main.c` still repaints these every loop; the meter was already fixed (throttled to data-change
events, 2026-04-04). Same treatment, or the component-level dirty tracking the TODO describes.
**Acceptance:** no full-area repaint when nothing changed; scope trace still updates live.

### B3. Waterfall colour scale
With `ref_level_db = 0` / `db_range = 80`, red = 0 dB and blue = −80 dB. A synthetic full-scale
square wave leaks across most bins, so the plot reads as a hot red field with thin nulls —
technically correct, visually useless. Consider auto-ranging the reference to the frame's
observed max, or a better default.
**Acceptance:** a 1 kHz square renders as recognisable harmonics on a dark floor.

## §C — Storage foundation (prerequisite for modules and user calibration)

### C1. W25Q region layer — **blocks C2, D1, and user-cal**
See `docs/roadmap.md` § "W25Q region layer". Not FatFs — a region table plus a bounds-checked
allocator. Requirements: explicitly **read-only** regions (everything stock owns — both FAT
volumes, `3:/System file/` and the UI assets included) enforced **by address, not by
convention**; bounds checks on every write/erase; a designated scratch region; no-op-write
elision; append-style records for frequently-updated data.
**Context:** `flash_fs_read()` / `flash_fs_write_atomic()` are currently FatFs stubs — only the
raw primitives are live, addressed absolutely. Nothing writes at runtime today, so this can be
built before the first writer exists, which is the right order.
**Wear is not the constraint** (100k cycles/sector; the danger is a stray erase destroying
stock data we cannot regenerate). **Acceptance:** host tests proving a write to a read-only
region is refused, and that a bounds violation fails closed.

> ⚠ **Correction (2026-08-14).** This section previously named
> `3:/System file/cal_ch1.bin` / `cal_ch2.bin` as the factory-cal files. **Those filenames
> were invented** — they are absent from the 16 MB dump
> `archive/w25q128_dump_2026_05_30.bin` and from every stock APP binary. The requirement
> above does not depend on them: read-only-by-address over the whole stock volume is the
> right rule regardless of what is in it. See
> `reverse_engineering/analysis_v120/factory_cal_truth_2026-08-14.md`.

### C1b. Factory calibration backup — **BLOCKED: there is no identified source to back up**

> ⚠ **Rewritten 2026-08-14.** As first written, this task said "read
> `3:/System file/cal_ch1.bin` and `cal_ch2.bin` and copy them to `FLASH_REGION_USER_CAL`."
> **Both filenames were invented.** They do not appear in the 16 MB dump
> `archive/w25q128_dump_2026_05_30.bin`, nor in any stock APP binary.
> `analysis_v120/meter_w25q_calibration_boundary_2026_06_06.md:167` had already flagged them
> as invented on 2026-06-06 and warned that production firmware must not probe them. The
> task as written was unimplementable: there is nothing at those paths to read.

Settings persistence is merged but its writes are gated OFF
(`SETTINGS_PERSIST_WRITES`, default 0, `firmware/src/util/config.h`). Turning them on still
wants a backup story first — but the backup cannot be specified until we know what, if
anything, is per-device and where it lives.

**What is actually established:**
- Stock restores a calibration-like table into RAM `0x20000358..0x2000044A` from a saved
  config, checks a sentinel at `ms[0x34E]` (`0x080261A8`), and when that sentinel is erased
  (`0xFFFF`) or zero it writes **hardcoded defaults compiled into the firmware image** at
  `0x080261BE..0x08026506` (default-path entry `0x08026198`). So a stock unit can run
  entirely on image-baked defaults with no per-device data involved at all.
- The only cal-shaped path stock references is `3:/System file/9999.bin` (string at
  `0x080BC841`). In every dump we have, that file exists but is **empty** — FAT entry
  `9999    BIN`, attr `0x20`, cluster 0, size 0 — so there are no bytes to copy and no
  format to decode.
- `analysis_v120/w25q128_flash_map_2026-06-13.md` swept the whole 16 MB offline: two FAT12
  volumes covering the entire chip, no raw region, contents = UI JPEGs + screenshots + FAT
  metadata + the empty `9999.BIN`. **No calibration on the W25Q**, which is why the region
  layer's `sysvol` protection is about stock's assets and volume integrity, not about a cal
  file. That analysis narrowed the saved-config source to **MCU internal flash
  `0x08006000`** — overwritten by our own app on both bench units, so no copy survives here.
- The two 301-byte per-channel arrays at state `+0x356` / `+0x483` are **oscilloscope
  roll-mode sample buffers**, not calibration (`analysis_v120/cal_data_myth_busted.md`);
  `FUN_08001830` pre-seeds them. Do not resurrect them as a cal source.
- Our own `flash_fs_load_factory_cal()` is already a deliberate fail-closed stub and
  probes no filenames — it is correct as-is and must stay that way.
- `scripts/validate_dmm_goal.py` has a standing gate that **fails the build** if
  `3:/System file/cal_ch1.bin` / `cal_ch2.bin` ever reappear in `meter_data.*` /
  `flash_fs.*`. Keep it.

**Open question, under investigation:** whether per-device factory calibration exists on
this platform at all, and if so where — SPI flash, MCU flash, the FPGA bitstream, or the
meter IC itself. Tracked in
`reverse_engineering/analysis_v120/factory_cal_truth_2026-08-14.md`. **Do not invent a
replacement story to unblock this task; that is exactly how the previous version got
written.**

**Caveat in the other direction:** absent from *our* dumps is not absent on *every unit*. Our
W25Q evidence is two byte-identical archived full-chip dumps plus one live read of bench unit
#2 — all units we had already reflashed. The June boundary analysis deliberately left
cross-unit comparison open and it is still open. A pristine or differently-provisioned unit
could carry data ours does not, which is another reason the read-only-by-address enforcement
in C1 stays regardless of what any given unit turns out to hold.

**What survives from the original task, and is worth doing once a source is identified:**
back up byte-exact into `FLASH_REGION_USER_CAL` (`0xF00000`, reserved and empty), read back
and compare before declaring success, then a restore path, and only then let user re-cal
write a *separate* record so nothing original is ever overwritten. A backup does not need
the byte layout decoded; re-cal does.

**Consumers of the RAM table, unchanged and still useful** (`reverse_engineering/CALIBRATION.md`):
the 20-byte-per-range entries starting at `0x20000358` are read by `scope_main_fsm` (indexed
by V/div) and by `gpio_mux_portc_porte` (flash `0x080088A4`) to compute the scope trigger
comparator DAC1 value; the meter's per-range DAC reference uses `0x20000394` (upper bounds)
against `0x20000358` (baselines), `DAC = ((upper − base)/divisor) × (offset + 100) + base`,
written to `0x40007408`. Note the entry-count claim is inconsistent across our own docs
(`CALIBRATION.md` says 12 × 20 B, `CLAUDE.md` says 6 × 20 B) and the *provenance* of the
table — "loaded from SPI flash at boot" — is an inherited assertion that the saved-config /
image-defaults finding above does not support. Both are open items for the truth doc.

*(`reverse_engineering/CALIBRATION.md` § "Per-Channel Calibration Arrays" has been corrected
as part of this cleanup — it now describes the 301-byte arrays as roll-mode buffers.)*

## §D — Modules (pure data, high community value, zero firmware risk)

Executable module code is **not achievable** on this hardware — the AT32 SPIM XIP window
collides with USB D−/D+ (see `docs/roadmap.md`). Modules are **data + a firmware-side
interpreter**, which is what `modules/` already is.

### D1. Module schema + loader spec
Define the JSON schema, the pool tenancy (`SHMEM_OWNER_MODULE` already exists), and the
interpreter's capabilities. **Depends on C1** for storage.

### D2. Seed modules
`modules/` has automotive, HVAC, ham radio and education stubs. Fill them out. This is the
single best contribution surface for domain experts who don't write firmware — CONTRIBUTING.md
already says so. Good candidate for splitting across several agents by domain.

- **E1.** PR #13 follow-ups (post-merge). **⚠ CORRECTED 2026-08-13 — both premises were stale

    from `input_handler.c:353` (`BTN_AUTO` while `current_mode == MODE_MULTIMETER`) and the
    path is reachable end to end: AUTO is bit 1 of the hardware-confirmed matrix (PE2+PC10,

    `meter_toggle_relative()` → `DCMD_REDRAW_ALL` → `draw_meter_screen()`, which renders the REL
    indicator (`meter_ui.c:823/860/878`). The only mode gate is `MODE_MULTIMETER`, entered by

  - *"`r->negative` is gated to submodes 0/2/3"* — **not on `main`.** `meter_data.c:381` reads
    `r->negative = (status & (1 << 0)) != 0;` with no submode gate, and `main` has no
    temperature submode at all (`METER_SUBMODE_COUNT == 10`, DCV…Capacitance).
  - **Both defects are real, but only on the unmerged PR #13 branch**, where BTN_AUTO is
    repurposed to DMM auto-range (orphaning REL) and a Temp submode 10 is added:
    `pr13-merge-test:firmware/src/drivers/meter_data.c:1252` reads
    `r->negative = ((submode == 0 || submode == 2 || submode == 3) && (status & (1 << 0)) != 0);`
    — submode 10 (Temp, `/* 10: Temp — 24.8 C */`) is excluded, so sub-zero temperatures can
    never render negative. **These are merge-time fixes, to be applied as part of §F5:**
    (a) drop the submode mask, or extend it to include 10; (b) re-expose REL on a button PR #13
    does not claim (CH1/CH2/MOVE are all unbound in meter mode).
- **E2.** ✅ **Done 2026-08-13.** `SHMEM_NEED_FFT` was 90112, which matched *neither* layout — it
