# Next-session plan (written 2026-09-12, after the EXP-25..28 meter session)

Priority-ordered. Section 1 is the critical path and is mostly code. Sections
2-4 are bench work gated on hardware being out. Section 6 is community, and it
has a latency target rather than a checklist.

Written against `168f713` on `main`: four build flavours green, 13/13 host
tests, working tree clean.

## 0. The sequencing rule that gates the whole meter track

**The `AA 55` TX header defaults OFF on `main`, and it must stay off until the
word table is correct.**

`meter_tx_header_aa55` is `false` at `fpga.c:1182`; the header is a runtime
toggle, not a boot default. That is deliberate. Ten of eleven submodes in
`stock_meter_cmd_low[]` select the wrong function, and submode 0 "DCV" sends
`0x14`, which is Auto. While the header is wrong the meter discards those words
unparsed, which is exactly why five months of readings looked fine: they were
all the SoC's power-on auto mode.

Flip the default before fixing the table and the failure mode inverts. The
meter would *obey* a wrong function word, so asking for resistance would select
something else, with relays actuating to get there. A wrong answer that the
instrument is actively driving is worse than a wrong answer nobody heard.

- [ ] **The corrected word table and the header default flip land in the same
      commit, table first.** Do not split them across commits, and do not flip
      the default "temporarily to test" on a build anyone else might flash.

Related invariant, already in the tree and easy to undo by accident:

- [ ] **The 4 Hz meter poll must keep going out unobeyed.** `fpga_send_cmd_keepalive()`
      leaves the OBEY bit clear so the poll frame carries `00 00`. The meter
      answers USART *traffic*, not accepted commands, so an unobeyed keepalive
      still produces data frames. Make it obeyed and every poll re-triggers a
      measurement and an autorange, which is continuous audible relay actuation
      and real mechanical wear. See EXP-26.

## 3. M3 — the acquisition record seam

Open since EXP-22 on 2026-09-03 and the deepest item on this list.

The record is not time-contiguous at its edges: stale data roughly one read
cadence old sits at indices about 32-96 and 864-928. The display trigger steps
over it with `SEAM_GUARD`, so the trace holds still, but **every whole-buffer
consumer still eats it.** That is what stands between this project and a live
FFT anyone should trust, and FFT on live data is the most visible feature still
at S0.

- [x] Root-cause session on readout alignment. DONE 2026-09-14 (EXP-39→42): the seam is the AUTO fallback reading mid-capture; PC0 works once the trigger level is inside the signal; edge-gated reads give a static body. Remaining: make the timebase-aware AUTO budget the default, hand reg 0x08 to the UI level, and characterise the invalid first 32–64 samples. The guard stays as the head cover.
- [x] Model rewritten 2026-09-22 (EXP-53/54): PC0 is a handover strobe on the read,
      the FPGA runs its own cycle (512 post-trigger, ~189 ms hold, roll), the loop
      is a poll. No "invalid head": the head was the seam = the FPGA's pointer.
      Committed records at the floor at every code; strobe → commit 1 ms.
- [ ] Only after the seam closes, promote FFT-live from S0 by consuming the live
      acquisition buffer in `guest-coldtrace`.

## 4. M2 — trigger modes

Not started, and worth raising in priority for a reason the milestone ordering
does not capture: **it is Tier 1 item 1 in `docs/community_wishlist.md`**, filed
there as the highest-recurrence user-facing complaint about the stock
instrument. It is the single most valuable thing on this document to somebody
who owns one of these and does not care how it works.

- [x] Trigger level owned by the UI + timebase-aware AUTO budget. DONE 2026-09-14
      (`3ec8fd9`, EXP-43): `fpga scope level` is the one writer of reg 0x08; the
      boot reconcile writes the UI level (0x80), not stock's captured 0xAD.
- [x] NORMAL / SINGLE capture. DONE 2026-09-14 (EXP-43→47): three defects on the
      way — NORMAL waited for an edge before the first read (a read starts the
      capture), the FPGA will not re-arm until one fill + ~200 ms after the
      trigger (EXP-46, now derived per timebase), and a level/timebase write
      drops the capture in flight (re-prime, `2c10625`). Acceptance on a fresh
      boot with nothing typed: NORMAL at 0x0E/0x10/0x11/0x12 edges = commits,
      holds above the signal, SINGLE one-shot 3/3. Spec S0 → **S1**, S2(b)(d)
      measured.
- [ ] S2 remainder: level-vs-ADC-code transfer (a), edge polarity (c).
- [ ] Fold the EXP-47 arms into `scripts/exp22_stability.py` (spec S3) rather
      than keeping a second harness.
- [x] Stock reads 04/05 pairs every ~29 ms (June capture) despite the re-arm
      bracket. ANSWERED 2026-09-14 (EXP-48/49): that is a poll rate — the June
      frames were untriggered (level 173 above a 165–168 input) free-run reads.
      Triggered captures are FPGA-bound at ~1/(fill + 190 ms) at every
      timebase (4.9/s at fast codes), no register we know changes it, and
      free polling returns torn records 25–50 % of the time. Keep the edge
      gate; the remaining win is ~200 ms latency (read at edge + fill).
- [x] ~~Origin of the ~190 ms holdoff~~ REFRAMED 2026-09-22 (EXP-53/54): it is a
      **hold** after the handover read, not a re-arm refusal — the FPGA keeps the
      completed record for ~189 ms after the read that strobed PC0, then rolls
      again. Where the constant lives (netlist) is still open but no longer gates
      anything: the loop polls for the handover (stock's 29 ms cadence).
- [ ] Trigger polarity: the FPGA fires on either edge (EXP-53 50j); test reg 0x02
      (`02 03` at boot) as the polarity select — S2(c) closes either way.
- [ ] Trigger level transfer: comparator = record + 28 on range 5 (EXP-53 50j);
      check one more range, then hand the offset to the UI marker — S2(a).
