# EXP-03 — Is our FPGA configuration deficient, or our runtime code?

- **Date:** 2026-08-17
- **Unit:** bench unit #1
- **Build:** stock V1.2.0, then `guest-warmtest-usart`
- **Status:** **CONFIRMED** — configuration exonerated, fault is in our runtime

## 1. Problem
Under our firmware: one scope channel, and the multimeter is dead
(EXP-02). Both were treated as unrelated. If our *configuration* were partially
functional, they would be one fault with one cause.

## 2. Hypothesis
Run our firmware on an FPGA that **stock** configured. If our config is the
problem, CH2 and the meter both come alive. If our runtime code is the problem,
both stay dead. A split means two independent faults.

## 3. Procedure
Warm handoff (`docs/fpga_warm_handoff_test.md`): deep power cycle → flash stock
→ **POWER** for a real boot (an IAP flash leaves stock in charge-display mode,
which skips FPGA init) → confirm both channels and the meter → **MENU+Power**
into upgrade mode, a *soft* reset that keeps the FPGA powered → flash
`guest-warmtest-usart`, which returns early from `fpga_init` before any config
sequence, so stock's SRAM configuration survives untouched. No unplugging, no
power cycling after the stock boot.

## 4. Control
| control | expected | measured | passed? |
|---|---|---|---|
| stock, two distinct shapes on the two jacks | tri + square | CH1 tri 414 Hz 1.88 Vpp, CH2 square 414 Hz 2.0 Vpp | ✅ |
| stock, two distinct tones | 100/250 Hz | CH1 82 Hz, CH2 208 Hz (same 0.82 factor) | ✅ |
| stock meter on a freshly configured FPGA | reads the cell | **1.61 V**, matching an external DMM | ✅ |
| our detector at the CH2 tone's bin | must SEE 250 Hz | 250 Hz on the working jack → bin 17 @ 23.4; 400 Hz → bin 27 @ 23.4; reverts | ✅ |

The last control is the one this project keeps skipping: the detector had only
ever *confirmed* a tone at bin 7, never been shown able to detect one at bin 17.

## 5. Results
On stock's own configuration, with our firmware running and reconfiguring
nothing:

| | result |
|---|---|
| meter | **dead** — 3 stock-proven frames, rx_bytes=0 |
| CH2 | **dead** — op04 and op05 both carry only the 100 Hz tone, same ~3.8-code converter offset |

Front-end pins swept in isolation on this same state:
| bus | effect |
|---|---|
| PE4/PE5/PE6 | **strong** — clean 8-position attenuator ladder (0.09 / 2.27 / 4.32 / 1.10 / 0.10 / **21.80** / 5.52 / 11.03), affects BOTH buffers identically |
| PB11/PB10/PA10 | **none** — all 8 codes leave both buffers at ~22 |
| PC12 | hard on/off — `0` passes, `1` kills to noise floor (contradicts our pin table's "PC12 HIGH = DC passes") |
| PA15 | none, toggled twice each way |

## 6. Blind spots
- Stock's FPGA **register** state (as opposed to its configuration) may not
  survive the MCU reset, so "stock's configuration" is preserved but "stock's
  runtime setup" may not be.
- Our firmware re-drives the front end at boot; this tests the end state, not
  what stock had set before the handoff.
- The screen observations of stock are user-reported, not instrument readings.

## 7. Conclusion
- **Established:** the fault is in our **runtime code**, not our bit-bang
  configuration. Stock had two channels and a working meter on this exact
  configuration minutes before our firmware booted on top of it.
- **Established:** `DONE_FINAL` is retired as a success criterion — stock's load
  is more functional than ours while both report the same status bit. *(Note:
  this inference came from the pre-handoff result and is weakened by the
  handoff itself, which shows config was never the differentiator.)*
- **Excluded:** the FPGA configuration; PC12, PA15, PE4/5/6, PB11/PB10/PA10 as
  the CH2 gate.
- **NOT excluded:** USART2 (still no validated instrument, EXP-02); PD12/PD13,
  PA6, PC11; whatever our boot path does that stock's working state does not
  survive.
- **Open contradiction:** maksidze measured PE4/5/6 as **CH2's** mux and
  PB11/PB10/PA10 as **CH1's** (issue #18, multimeter + routing diagram). On this
  unit PE4/5/6 controls the jack stock labels **CH1**. Either our channel naming
  is inverted or the mapping differs by board revision. Unresolved.
